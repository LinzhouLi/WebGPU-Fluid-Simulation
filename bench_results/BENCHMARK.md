# WebGPU 流体渲染 Code Agent Benchmark

## 1. 文档目的

本文档记录本次 Code Agent 测试的任务目标、测试环境、参考实现、评测方法和实验进展。它同时作为后续收集不同模型运行记录、代码、截图、性能数据和人工评审结论的统一索引。

本测试希望考察的不是模型能否机械补齐若干文件，而是模型能否在一个真实 WebGPU 图形项目中完成以下闭环：

1. 阅读既有仿真与渲染架构；
2. 阅读并提炼图形学论文；
3. 将论文方法转化为可运行的 WGSL/WebGPU 多阶段渲染管线；
4. 正确处理坐标空间、深度、纹理格式、混合和 GPU 资源生命周期；
5. 在视觉质量、正确性、性能和工程质量之间做出合理取舍；
6. 自主构建、运行、观察画面并迭代修复。

这与目标岗位的核心工作相对应：定义渲染实现的质量标准、设计有区分度的评测任务，并为模型输出提供可复核的标注依据。

### 2.2 基线状态

基线已经具备：

- 可运行的 WebGPU PBF/SPH 粒子仿真；
- GPU 哈希网格邻域搜索和并行前缀和；
- 兔子下落、立方体下落、水滴、双溃坝和边界等场景；
- 相机、方向光、深度缓冲和一套 Sea cubemap；
- `NarrowRangeFilter.pdf` 论文；
- TypeScript + Vite 构建环境。

基线渲染器 `src/renderer/rawParticles` 为每个粒子实例化一个 `SphereGeometry(0.007, 8, 8)`，使用 Lambert 漫反射着色。它可以显示仿真结果，但画面仍是大量离散小球，且每个实例需要处理低模球体的全部顶点和三角形。

### 2.3 参考实现的主要管线

`main` 中的参考实现采用以下过程：

```text
粒子位置缓冲
  -> billboard 深度光栅化（每粒子 4 顶点）
  -> 眼空间深度图 r32float
  -> billboard 厚度/体积累加图 r16float
  -> 横向 Narrow-Range compute pass
  -> 纵向 Narrow-Range compute pass
  -> 根据深度重建眼空间位置和法线
  -> cubemap 反射/折射 + Fresnel + 厚度吸收
  -> 合成至画布
```

参考实现还提供 PBR、无折射、Diffuse、Normal、Depth、Thickness 和 Position 等调试显示模式。这些模式有利于人工确认中间结果，但不是要求模型逐项复刻的硬性条件。

## 3. 给模型的原始任务

> 当前项目是一个WebGPU的流体仿真项目，使用的是粒子的仿真方式，但是渲染部分还很粗糙，用的是最简单的shading渲染每个粒子小球，你帮我参考NarrowRangeFilter.pdf这篇论文（论文就在项目目录下），实现一个更好的流体渲染结果：  
> 1. 参考论文中的深度图滤波方式，平滑粒子小球的深度图。  
> 2. 在screen-space完成流体渲染，你需要考虑流体的折射和反射，需要去查环境光贴图。  
> 3. 将当前的小球渲染改成更高效的渲染方式，使用billboard渲染屏幕空间的粒子，可以接受投影误差，将球形粒子的透视投影近似成屏幕空间的圆形。

正式对比时应保持该 Prompt 不变。任何追加提示、人工报错信息或环境修复都要逐条记录，因为它们会改变模型独立完成任务的程度。

## 4. 目标实现的最低语义要求

### 4.1 Billboard 粒子光栅化

- 不再为每个粒子绘制完整球体网格；
- 每个粒子使用一个面向相机的 quad，典型实现为 4 顶点 `triangle-strip`；
- fragment shader 根据 quad 局部坐标丢弃圆外像素；
- 根据球面方程近似恢复球面前表面深度，而不是给整个圆写入同一深度；
- 正确参与场景深度测试，不能无条件覆盖前景网格。

### 4.2 深度与厚度缓冲

- 生成可供后处理读取的流体深度纹理；
- 明确深度采用的空间和符号，例如正值眼空间距离；
- 背景/无粒子像素有稳定哨兵值，并在滤波与合成时正确处理；
- 为折射吸收生成厚度或体积近似。可以使用加法混合累加粒子核，也可使用等价方案；
- 纹理尺寸、格式、usage、采样类型及 bind group 声明相互匹配。

### 4.3 Narrow-Range Filter

论文方法的关键不只是“做一次模糊”，而是只直接使用中心深度附近的样本，并对范围外样本区别处理：

- 过近、属于前景遮挡面的样本应被排除；
- 过远样本不直接混入，而应钳制到中心值附近，从而在断层边缘形成自然曲率；
- 成对考察中心两侧样本可维持核的对称性，降低倾斜背景在遮挡边缘的偏差；
- 动态扩展允许深度范围，可避免掠射角下连续表面被误判为断层；
- 高斯空间权重、阈值和核大小应有清晰含义；
- 使用横向、纵向两次 1D pass 是可接受的高效近似。若实现论文中的小型 2D clean-up pass，应作为质量加分项；
- 不能把普通高斯模糊或双边滤波仅改名为 Narrow-Range Filter。

论文令滤波核的屏幕尺寸随眼空间深度变化，以保持近似固定的世界空间尺度。参考答案使用可调的固定像素核，是工程简化而非论文的完整复现；模型如果正确实现深度相关核大小，应加分而不是因偏离参考代码扣分。

### 4.4 屏幕空间合成

- 从滤波后深度重建眼空间位置；
- 通过相邻像素差分或等价方式重建稳定法线；
- 将视线、法线以及反射/折射方向放在一致的坐标空间中；
- 使用水的合理折射率，例如约 `1.333`；
- 使用 Schlick Fresnel 或物理意义相当的近似混合反射与折射；
- 使用 cubemap 查询环境反射和环境折射；
- 使用厚度控制透射衰减或着色，使薄层和厚层有可见差异；
- 无流体像素不得污染原场景。

## 5. 验收门槛

以下任一问题通常意味着任务不能判为“成功完成”：

1. `npm run build` 失败；
2. 页面无法启动或出现未处理异常；
3. WGSL 编译、pipeline 创建、bind group 或 WebGPU validation error；
4. 流体完全不可见、全屏覆盖、深度方向错误或持续闪烁；
5. 仍以球体网格作为最终粒子表面渲染，没有 billboard；
6. 没有真正的深度滤波 pass；
7. 没有最终 screen-space 合成，或没有环境反射/折射；
8. 为完成渲染而破坏了原有 PBF 仿真和场景切换。

完成状态建议统一标为：

- **成功**：通过全部硬性门槛，三个核心要求均有正确、可用的实现；
- **部分完成**：可以运行，但缺少一个核心要求，或存在明显视觉/正确性问题；
- **失败**：不能构建/运行，或输出与任务目标基本无关。

## 6. 评分细则（100 分）

硬性门槛先决定完成状态；分数用于区分同一状态内的实现质量。

| 维度 | 分值 | 关注点 |
| --- | ---: | --- |
| 功能完整性 | 30 | billboard、深度、厚度、滤波、全屏合成、反射折射是否真正串联 |
| 图形与数学正确性 | 20 | 坐标空间、Reverse-Z、深度重建、球面深度、法线、Fresnel、折射率和 gamma |
| 视觉质量 | 20 | 连续流体表面、边缘曲率、断层保持、掠射角稳定性、闪烁和条纹 |
| 性能与资源开销 | 15 | 每粒子顶点数、pass 数、dispatch、临时纹理、共享内存、重复分配、GPU 时间 |
| WebGPU API 质量 | 10 | 格式/usage/layout 匹配、越界保护、尺寸取整、资源生命周期和 validation cleanliness |
| 工程质量 | 5 | 结构清晰、改动聚焦、参数可调、注释准确、无大段死代码 |

### 6.1 视觉检查场景

至少检查以下场景和观察角度：

| 场景 | 主要观察目标 |
| --- | --- |
| Bunny Drop | 初始离散形状能否快速形成连续表面；运动时是否闪烁 |
| Cube Drop | 大面积近似平面是否平滑；边缘是否过度鼓起或塌缩 |
| Water Droplet | 前景液滴与底层液面之间的深度断层是否被错误连接 |
| Double Dam Break | 大量高速粒子下的稳定性、覆盖范围和性能 |
| Boundary | 流体与实体网格之间的深度遮挡是否正确 |
| 低角度观察 | 动态范围或等价策略能否避免连续表面断裂 |

每个结果建议保存相同时间点、相同画布分辨率、相同相机位姿的静态截图，并补充一段运动视频。只凭单张最佳角度截图不足以判断时序稳定性。

### 6.2 性能记录

在固定设备、浏览器、分辨率、场景、粒子数和相机下记录：

- 平均 FPS 与 1% low；
- 仿真关闭或暂停时的纯渲染 GPU 时间；
- 深度 pass、厚度 pass、滤波 pass、合成 pass 的 GPU 时间（设备支持 timestamp query 时）；
- 每帧 draw call、dispatch 次数和主要纹理显存估算；
- 与基线球体实例渲染、`main` 参考实现的相对变化。

模型声称“更高效”不能只依据代码形态；billboard 顶点量下降是结构证据，最终性能仍应通过 profiling 复核。

## 9. 从真实任务抽象为标注平台样例

### 9.1 样例输入

- **Repository state**：固定到基线提交的完整仓库；
- **Reference material**：仓库内的 `NarrowRangeFilter.pdf`；
- **User request**：第 3 节原始 Prompt；
- **Environment contract**：Node/包管理器、WebGPU 浏览器、GPU、运行命令和时间限制；
- **Allowed tools**：文件、终端、浏览器及是否允许联网；
- **Hidden reference**：`main` 的参考实现、参考截图和性能区间，不向被测模型暴露。

### 9.2 样例输出

- Agent 完整轨迹：分析、工具调用、错误、修复和最终说明；
- 最终代码 patch；
- 构建与运行日志；
- 固定场景截图/视频；
- 性能指标；
- 人工评分与错误标签。

### 9.3 标注结构

建议把标注拆成三层：

1. **可自动验证事实**：构建是否成功、是否存在 validation error、是否创建 billboard draw、是否存在深度/厚度纹理与 compute filter、是否采样 cubemap；
2. **专家可复核判断**：坐标与深度数学是否正确、滤波是否符合论文语义、资源设计是否合理、画面是否稳定；
3. **偏好排序**：在都能运行的候选之间，综合视觉、性能、正确性与工程质量进行 pairwise preference，并明确胜出的证据。

错误标签可以包括：`build_failure`、`wgsl_compile_error`、`webgpu_validation_error`、`depth_space_error`、`billboard_geometry_error`、`not_narrow_range_filter`、`filter_boundary_artifact`、`normal_reconstruction_error`、`reflection_space_error`、`refraction_error`、`missing_thickness`、`resource_waste`、`simulation_regression`、`insufficient_verification`。

### 9.4 为什么该样例有区分度

该任务同时要求论文理解、跨文件架构修改、GPU API 使用、WGSL 编程、渲染数学、视觉判断和真实性能验证。弱模型可能生成看似完整但无法编译的代码；中等模型可能完成 billboard 和后处理框架，却在深度空间、滤波边界或折射方向上出错；强模型还应主动运行应用、查看中间纹理、修复 validation error，并通过 profiling 解释实现取舍。

如果模型整体能力提升，应逐步提高评测难度，而不是只检查能否跑通：

- 删除对具体 pass 和技术路线的提示，只提供视觉目标与论文；
- 加入窗口 resize、非 32 倍数分辨率、不同 FOV 和高 DPI；
- 加入多个深度相邻但空间不连续的流体层；
- 要求自动截图回归和 GPU timestamp profiling；
- 要求在固定帧预算或显存预算内达到视觉阈值；
- 加入缺陷参考实现，让模型识别并修复，而不是简单模仿；
- 使用隐藏场景检查过拟合。

## 10. 当前评测有效性风险

### 10.1 Git 历史隔离（已解决）

开发仓库中的 `benchmark/raw-particles-baseline` 是 `main` 提交 `49a38e3` 的后继分支，因此直接把完整开发仓库交给 Agent 会存在从 Git 历史读取参考实现的可能。

实际测试环境会完整删除 `.git` 目录，只向模型提供基线工作树文件。模型无法访问分支、父提交、refs、reflog 或 Git 对象，因此不能通过版本历史恢复 `main` 的参考实现。参考答案、参考截图与评分材料继续保留在评测侧，不进入模型可访问环境。

归档实验时应记录“测试副本不含 `.git`”这一环境条件，确保不同模型使用相同的隔离方式。

### 10.2 `bench_results` 当前被整体忽略

根目录 `.gitignore` 包含 `bench_results`。因此本文档和未来模型结果默认不会进入 Git 变更。若结果需要版本管理，应移除该忽略项，或仅忽略体积较大的视频、构建产物和临时文件。

### 10.3 参考实现不是逐行标准答案

`main` 是可运行的工程参考，但并不完整复现论文的所有细节。例如它采用固定像素滤波核和两次 1D 可分离近似，没有实现论文建议的最终小型 2D clean-up pass。评分应基于任务语义、画面与 profiling 证据，而不是与 `main` 做文本相似度比较。

### 10.4 环境不固定会削弱性能结论

WebGPU 性能受 GPU、驱动、浏览器版本、窗口分辨率、DPR、粒子数和场景影响。未固定这些条件时，只能评价结构性效率，不能据 FPS 对不同模型做可靠排序。
